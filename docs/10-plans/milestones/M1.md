# M1 — Cross-project FVP over my own Markdown

**Outcome.** The user can point FlowPilot at two independent Markdown folders or vaults, see their tasks and projects as one portfolio, edit in either place without losing anything, and run an authentic FVP session across projects that survives switching between Work and Personal contexts. Optional weekly outcomes, a deterministic summary and basic attention signals exist. Nothing requires an inbox-processing or review step. No AI. M1 starts only after the [[M0]] experience definition is signed off.

## Gate criteria (human-checked, with evidence)

- [ ] **G1** — Two independent folders/vaults are registered (one may be read-only) and their tasks and projects appear in one portfolio view. *Evidence: e2e test + manual demo on the user's real vaults.*
- [ ] **G2** — An edit made outside FlowPilot (editor, Obsidian, sync tool) appears in the app without a restart; an edit made in the app lands in the original file without clobbering a concurrent external change. *Evidence: integration tests for watch + conflict-safe write.*
- [ ] **G3** — A cross-project FVP session can be started, interrupted and resumed (including after an engine restart) with chain state intact and the rules chosen in the FVP spec honoured. *Evidence: rule-level unit tests + e2e.*
- [ ] **G4** — Switching Work ↔ Personal changes the eligible tasks without discarding either context's session; external edits apply silently, except that a change to the pinned benchmark shows a one-line, non-blocking notice. *Evidence: e2e.*
- [ ] **G5** — A few weekly outcomes can optionally be set, and projects without outcomes stay visible. An on-demand deterministic summary shows completions and re-entries per project, plus idle, waiting and deadline signals (D20). Basic attention signals (e.g. no recent activity, missing next action, overdue) are shown without AI. New items land on the list, and nothing must be processed or reviewed before FVP can continue. *Evidence: e2e.*
- [ ] **G6** — The user's files remain plain, portable Markdown: removing FlowPilot leaves them readable and correct. *Evidence: fixture diff review.*

## Specs (expected; written one at a time via `write-spec`)

Ordered by dependency. Each resolves part of [[flowpilot-concept]] §10 "Open questions" and takes its UX from the signed-off [[M0]] experience overview.

1. **Architecture and stack** — engine runtime/framework, UI framework (Angular is the candidate), local database, Markdown parser, file watcher, API style, packaging → ADRs.
2. **Markdown task model** — task identity, project association, status, ordering; what lives in Markdown vs app storage.
3. **Source registry and sync** — multiple roots, read-only sources, overlapping paths, watching, reconciliation, conflict-safe writes.
4. **FVP engine** — the exact rules (chain, re-entry, continuation), sessions per context, stale-state handling.
5. **Contexts and eligibility.**
6. **Portfolio overview** (God's-eye) — the first UI surface.
7. **Weekly outcomes, summary and attention signals.**

Specs may merge or split during `write-spec`; this list is a plan, not a contract.
