# M0 — I know what using FlowPilot will feel like

**Outcome.** Before any product code exists, the user has a signed-off picture of the FlowPilot experience. It covers the interaction model, how the main surfaces connect, and what "fluid and pleasant" concretely means. It has been tested against realistic example tasks with designs and a few throwaway POCs, and it is good enough that the [[M1]] specs can take their UX from it instead of inventing it.

## Constraints from the user

- **Stay close to FVP.** The FVP mechanics lead; any visual metaphor (tiles were one rough idea) must serve them, not replace them. Tiles are optional and may be dropped entirely.
- **No maintenance rituals.** There is no inbox processing and no weekly review step. Capture goes straight onto the list, clarification happens when an item comes up in a pass, and summaries replace reviews (see [[flowpilot-concept]] revision 2026-11-01).
- **Feel matters most.** Operating the system should be fluid and pleasant. That has to be pinned down concretely enough to test.
- Technical questions are out of scope here unless a POC shows that a UX choice constrains the stack.

## Gate criteria (human-checked, with evidence)

- [ ] **G1** — A shared sample portfolio and its scenarios (including one long, 50+ item list) exist, and every design and POC uses them. *Evidence: `docs/00-vision/experience/scenarios.md`.*
- [ ] **G2** — An experience overview describes the interaction model, surfaces and flows, and defines "fluid" concretely (interaction rules, response targets). Its open questions are resolved or explicitly deferred. *Evidence: `docs/00-vision/experience/overview.md`, status `approved`.*
- [ ] **G3** — Each scenario has been walked through in a design (Claude Design or equivalent), and the user has reviewed each one. *Evidence: links in the overview.*
- [ ] **G4** — The 2–3 riskiest interactions were tried hands-on as throwaway POCs, and each has a findings note. *Evidence: `docs/60-research/ux/`.*
- [ ] **G5** — The no-maintenance constraint holds in every scenario: no step makes the user process, triage or review before getting back to work. *Evidence: scenario walkthroughs.*

## Work items (not specs; this milestone produces design docs, not build specs)

1. **Sample portfolio and scenarios.** A fictional set of 3–4 projects plus a personal area, with realistic items, and the scenario stories that exercise them.
2. **Experience overview.** The interaction model and principles, with numbered open questions first.
3. **Design explorations**, one per scenario or surface.
4. **POCs** for the riskiest mechanics, e.g. the FVP pass, capture mid-flow, and the context switch. The code lives in `poc/`, outside `apps/`/`packages/`, and is thrown away afterwards.
5. **Consolidation.** Fold the findings back into the overview, ready for sign-off.
